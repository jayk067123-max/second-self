## 一、章节主张

本项目没有让 AI 自由生成，而是把「人定意图、AI 出方案、人收敛偏差」做成了一套可审计的流程：每一轮交互前有意图卡，交互中有约束清单，交互后有修正记录，并与 git 提交一一对应。

## 二、要点清单（14 条）

### 1. 意图前置：先写卡，再发 Prompt
- 主张：Prompt 不是想到啥说啥，而是先落一份「目标 / 上下文 / 约束 / 禁止事项 / 验收标准 / 本轮求助点」六项卡，再照卡发问。
- 作用：把意图从"脑子里的想法"变成"纸面上的契约"，事后可核对偏差。
- **B 项目落地**：001/002/003 三张卡在对应轮开工前建好。002 卡在发 Prompt 前就把「重复规则必须解析成标准重复字段」「相对时间按运行当天推算」写成验收标准，不给 AI 事后解释空间。
- 证据：`docs/prompts/TEMPLATE.md`；`docs/prompts/001-*.md` §1

### 2. 每轮只压一个可验收增量
- 主张：一个编号只做一件事，且必须能用命令/点击验证。不做"顺便把别的也做了"。
- 作用：改动可归因，出问题能定位到具体一轮。
- **B 项目落地**：三条链 = ①骨架与四层架构 ②群通知文本 → 结构化任务 JSON ③冲突检测 + 重排。002 只做"文本进、JSON 出"，重排算法严禁这一轮沾手；003 只做检测与重排，不动解析器。
- 证据：`docs/prompts/INDEX.md` 编号与「对应模块」列

### 3. 上下文按需喂，不做全量倾倒
- 主张：不把整个仓库丢给 AI。只贴本轮要动的文件 + 接口签名 + 相关类型定义，其余靠"现状一句话"补。
- 作用：控 token，也防 AI 被无关代码带偏。
- **B 项目落地【预写】**：002 只喂三样——数据模型 `types` 里 Task 的字段定义、解析函数的空壳签名、一份真实课表/群通知样本文本；不喂路由层、不喂 UI。
- 证据：待回填（002 §1「上下文」列需写明贴了哪几个文件）

### 4. 负面约束先于正面描述
- 主张：Prompt 里「不许做什么」比「要做什么」更能防跑偏。明确：不改数据结构、不加新依赖、不动指定文件、不重写整个组件。
- 作用：这是防"AI 顺手重构导致大面积回归"的主手段。
- **B 项目落地【预写】**：002 的禁止事项写死三条——不许自行新增/改名 Task 字段；不许把"下周"按固定 `+7 天` 硬算；不许引入 NLP 分词库，只用既有 LLM 调用。003 的禁止事项：不许改解析器的任何一行代码。
- **本项目最硬的样本（已发生）**：001 子步 1 的技术选型收敛——AI 给出的数据层方案是 `drizzle-orm + better-sqlite3`，人类以「评委机器装 VS Build Tools 才能编译原生模块，会拖死 10 分钟复现」为由否决，改为本地持久化适配层。负面约束写成"不许保留需要 node-gyp 编译的原生依赖"，比"请选轻量方案"有效得多。见 `001-skeleton-architecture.md` §4 行 1。
- 证据：待回填（对应轮 §1 禁止事项 + §4 表里的越界拦截实例）

### 5. 接口与数据结构由人先定死
- 主张：函数签名、字段名、类型由我写进 Prompt，AI 只填实现体，不允许自行改接口。
- 作用：一次到位率最高的手段，也是"结果不是拼接"的核心证据。
- **B 项目落地【预写】**：002 的输入输出签名与 Task 字段（标题/日期/开始/结束/重复规则/来源原文/置信度）由全栈手先定，我抄进 Prompt 并附「不得变更」字样。
- 证据：待回填

### 6. 验收标准写在前面，用勾选表收盘
- 主张：验收标准在发 Prompt 前就写好，AI 交付后逐条 ✅/❌，不一致就再下一轮。
- **B 项目落地【预写】**：002 四条验收——①"每周三 19:00 到 21:00"解析为标准周重复字段 ②"下周三"按运行当天推算正确 ③JSON 字段齐全可解析 ④缺时间信息的条目落入"待确认"而不是丢弃。
- 证据：`TEMPLATE.md` §1 验收标准 / §5 逐条对齐

### 7. 偏差即冻结：真实出错轮次当场留痕
- 主张：AI 写歪的那一轮不重写、不美化，当场截图存 Prompt 原文，作为「我如何引导修复」的证据。
- 作用：过程可信度来自瑕疵，不来自完美。
- **B 项目落地**：002 预计会漏「每周三 19:00-21:00」这类重复规则或算错"下周"——**真实出现即冻结**，不提前摆拍、不事后重写；003 预计会把单日总时长算坏导致正常日程被误判超载，同样当场留。
- 证据：`RECORDING-GUIDE.md` §7

### 8. 引导修复的四段式记录法
- 主张：每次修正按「现象 → 我的判断 → 我下的指令原文 → AI 响应结果」记。
- 作用：证明是人引导 AI，不是 AI 自愈。
- **B 项目落地**：003 的回归 Bug 定位必须记全四段——我如何先用"改前能跑的用例"证明是回归、如何把「不许动解析器」再压一次、AI 改后如何复测两条原本正常的日程。
- 证据：`TEMPLATE.md` §4 表格

### 9. 记录与提交同批、双轨可追
- 主张：代码、Prompt 记录、INDEX 索引同一次提交；commit message 带 `[prompt:NNN]`；原始截图/录屏另存 `05-Prompt与演进记录/`。
- 作用：形成"md ↔ commit ↔ 原始素材"三角互证，防"一次性大提交"质疑。
- **B 项目落地**：三条链的提交信息形如 `feat(parse): 群通知文本结构化 [prompt:002]`；骨架那轮为 `feat(skeleton): 四层架构骨架 [prompt:001]`。
- 证据：`RECORDING-GUIDE.md` §2 §4；`git log` 待回填

### 10. 补记必须标注，不冒充原文
- 主张：事后补写的记录标「补记」，靠回忆重建的 Prompt 标「【回忆重建，非原文】」。
- 作用：主动暴露证据等级反而提升可信度；造假一旦识破全盘归零。
- **B 项目落地**：000 号卡已属真实记录；001 起一律当场建卡，13 天窗口下没有补记余地，出现补记即为红灯。
- 证据：`RECORDING-GUIDE.md` §6

### 11. 为什么结果不是拼接的（正面论证）
- 主张：三条链各自落在不同的时间窗口与不同的代码层，每轮改动文件可从 md §3 与 `git log --stat` 双向对上；意图卡里的验收标准在提交前已被逐条勾选，不存在"最后一次性贴入成品"的时间窗口。
- **B 项目落地**：骨架轮只动目录与空壳、解析轮只动 parser、检测轮只动 conflict 与 UI 结果页——三层可分别 `git log --stat` 验证互不重叠。
- 证据：待回填（三段 `git log` 时间线与三个 md 的对应图）

### 12. 凡是可能被怀疑造假的地方，都让它在画面上自己声明
- 主张：与其在文档里保证「我们没有摆拍」，不如**把这句话做成产品行为**——凡是可能被质疑"是不是把 mock 冒充真模型""时间是不是实时读的"的地方，都由系统自己在屏幕上写出来。
- 作用：把"请相信我们"换成"你自己看，它自己写着"。质疑者只要在同一帧里看到声明，就不需要读任何文档。
- **B 项目落地（已实现，可截图举证）**：
  - 无 `LLM_API_KEY` 时，`npm run parse` 的**第一行固定打印** `[demo mode] 未配置 LLM_API_KEY，使用固定规则的本地 mock 输出（非真实模型返回）`——录像里那一帧就是"没拿 mock 冒充真实模型"的直接证据；
  - 同一条判断在图片入口上是**诚实失败**：`src/ai/tasks.ts` 第 138 行注释写明"demo 模式必须诚实失败：没有密钥就没有多模态能力，任何『假装识别成功』……"，返回文案为「当前未配置 LLM_API_KEY（demo 模式）」，`issues` 里再补"不会假装已经识别成功"；
  - 演示时钟角标常驻顶栏「演示时钟 2026-10-19 09:00」，且**角标自己写出来源**——`src/app/planner/page.tsx` 第 80 行按 `demoClock.source` 渲染 ` seed` 或 `系统时间`；第 34 行取 `usePlannerStore((s) => s.demoClock)`、第 38 行 `new Date(demoClock.iso)`。**时间来自 store 的注入值，不是页面读的**，且"这是 seed 的时间还是系统时间"由界面明说；
  - 判定层不读系统时钟：`src/domain` 内 `Date.now()` 零处、`new Date()` 无无参调用。对外统一口径是 **「页面/组件不读系统时钟（`src/ui` + `src/app` 32 个文件，`Date.now(` 0 命中）；`new Date(` 4 处均为构造注入值或服务端自检时间戳；系统时钟只在数据层三处使用并标来源；导入 seed 后全链路切到种子 `demoNow`」**。
- 证据：`scripts/parse.ts` 第 11 行（约定）、第 118 行（打印语句）；`src/ai/tasks.ts` 138 / 151 / 152 行；`src/app/planner/page.tsx` 34 / 38 / 80 行；`src/ui/composites/IntakePanel.tsx` 41 行；`src/app/api/health/route.ts` 28 / 84 行；`src/data/store.ts` 80 / 90 / 285 行（另有 227 / 228 / 241 / 242 行是 `new Date(毫秒数)` 时间戳格式化，不读时钟）；`RECORDING-GUIDE.md` §4.5 第 9 条（"判定层可复现"的适用范围限定）；行号对应 `a46d9b4`（2026-10-18 21:46），取号命令见 `004` §3

### 13. 不确定必须外化为可见标记，否则等于替用户拍板
- 主张：模型估出来的值（时长、地点、日期）不能在数据里悄悄标一个 `needsReview` 就算完事，**必须在界面上以人眼可见的方式标出来**（如「约 90 分钟 · 待确认」）。数据层的不确定不等于用户知情。
- 作用：这是"不猜测"从设计原则落到产品行为的最后一跳。不做这一跳，前面所有的置信度、待确认通道都白做，产品退化成"猜了一个数还骗用户说确定"。
- **B 项目落地**：`needsReview` 为任务级信号（`src/` 内 20 处），与 `needs_repair`（设计期名、代码从未采用，返回 `ok:false` 的调用级失败态）严格区分——两者名称近形，已在 `ARCHITECTURE.md` 加术语区分段，防评委误读成"字段名都没统一"。007 的两条裁定（一屏一问不设上限、不把指纹当判定依据）同属这一族判断：**当机器无法确定时，把决定权交回用户，并且让用户看见这是一次决定。**
- 证据：`007-missing-info-clarify.md` §6；`ARCHITECTURE.md` 术语区分段；`003` §4 第 4 段（done 未过滤形同"静默降级"的反例）

### 14. 「完成」必须由引用链证明，不由完成声明证明
- 主张：一个功能"做完了"的判据不是文件存在、不是测试通过，而是**它在产品里有一个用户能点到的入口**。凡是新建的组件、函数、store action、素材，都必须能追到至少一处引用/调用/读取，否则按"没做"计。
- 作用：这一类问题是"看起来完成、实际摸不到"——功能全齐、测试全绿、评委却看不到，而**看不到就等于没有**。它专门骗过只读代码摘要、不跑产品的自检。
- **B 项目落地的四张病例（都真实发生过，都可 grep 复现）**：
  1. **写了但没入口**：`TimetableReuploadPanel.tsx` 文件存在、面板/解析/覆盖计划/落库四件俱全，但曾全仓 0 处引用——**死组件**。后被挂进 `TodayScreen.tsx`（import 在 18 行、使用在 202 行）才真正"完成"。教训：**"写好了"和"产品里有"是两个不同的验收状态。**（口径提醒：主管chief 22:5x 报"0 处引用"、Prompt官 22:55 实测"3 处"——同一件事两个值，因为中间那次挂载提交发生在两次测量之间；**报红也要带时刻与 HEAD**，否则"已修好"和"还没修"分不清。）
  2. **双名并存**：`needsConfirmation` / `needsReview` 两种写法同时存在，字段"能用"但看着没统一。
  3. **双裁决器**：`planner.validatePlan` 与 `reflow.adjudicateProposal` 并存，谁说了算无法判定。
  4. **口径混说**：`Date.now` 与常量时钟混着讲，功能没问题，一 grep 就前后矛盾。
