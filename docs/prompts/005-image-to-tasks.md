## 1. 意图卡

| 项 | 内容 |
|---|---|
| **目标** | 用户贴一张课表/群通知截图，能出**可核对的任务草稿**；并且原图上每一行都有归属——要么变成任务，要么进「没看懂，请你确认」列表，**不许静默丢行** |
| **上下文** | ①既有契约：`ParseResponse`（`src/domain/schemas/api.ts`）已由文本链 002 定死，本轮不得另起一套 ②既有护栏：`src/ai/prompts.ts` 里的 14 条规则、`guarded.ts` 的分级重试与限流 ③既有 UX：`TaskCorrectionTable` 的黄色 needsReview 行已可用 ④前置轮次：002（文本结构化） |
| **约束** | 复用 002 的**同一份输出契约**与**同一套逐条校验**，图片与文本只在"消息体"和"完整性校验方式"两处不同；新增路由不得绕过 `guarded` 限流；demo 模式（无 key）下**不许假装识别**，必须给明确降级提示；不新增 OCR/图像库依赖 |
| **禁止事项** | ①不许引入 tesseract/ocr 类依赖 ②不许把图片解析结果直接写库，必须过人工修正表 ③不许在整图无日程时编造任务（只允许给一条 `title="图片里没有找到日程信息"`、`needsReview=true` 的占位）④不许因"读不清"就丢掉那一行 ⑤不许改动 `conflicts` / `reflow` / `snapshot` |
| **验收标准** | ①非法 body（非 JSON）返回 4xx 且不 500 ②超过限流阈值返回限流响应而非排队 ③无 key 的 demo 模式启动不白屏、给出明确提示 ④`coverage.uncovered` 非空时 UI 必须展示 ⑤`needsReview=true` 的条目在修正表里高亮且改完即清 ⑥真实素材 `notice.txt` 的五个歧义点至少不崩、模糊项标 needsReview |
| **本轮求助点** | 只解决"图片 → 结构化草稿 + 完整性可核对"这一件事；不要顺手做追问交互（那是 007）、不要顺手改课表重传（那是 006） |

## 2. 我的 Prompt（原文）

> **来源与性质**：渠道＝群聊「Vibe Coding 赛队」，发言人＝主管chief，**群消息本身不带时间戳**，故时间以执行方本机的执行区间为界（实现落在 10-18 17:00 至 18:16，`npm run verify` 18:15:20 全绿）。原文由执行方（全栈手）从他自己的会话记录逐字贴回，**未做润色**。这段是"下发给执行方的指令"，不是"我对着 AI 编辑器敲的 Prompt"——两者在本书里必须分清，不能混写成一句。

```text
@全栈手 先落「不许静默丢弃」的完整性校验和图片入口的数据链路，这是这轮的地基；@Prompt官 新增两张意图卡：图片→任务、课表重传覆盖＋主动追问。@映像官 分镜里补「重传课表自动覆盖」这段
```

> **这条原文证明了什么**：§1 的禁止事项④「不许因读不清就丢掉那一行」**不是我事后按实现倒推的**——下发时第一句就是"不许静默丢弃"。这是本卡最硬的一条证据，比 §5 的用例数有用得多。
> 仍未留存的部分：执行方拿到指令后在这个入口上具体怎么问 AI 编码器、AI 第一版怎么答，无原文，**不补写**。

## 3. AI 的产出（磁盘可核事实）

- 路由：`src/app/api/ai/parse-image/route.ts`（限流 5 次/分钟，独立 key 前缀 `parse-image:`）
- 完整性：`src/domain/completeness.ts`——"任何一行原文都不许静默丢掉"的纯函数实现
- 契约：`src/domain/schemas/api.ts` 增 `coverage`（原文每行有没有归属）
- UI：`IntakePanel` 增"逐行核对完整性"步骤；`UncoveredNotice` 是这条约束的用户可见面
- 测试：`tests/ai/parse-image-route.test.ts`、`tests/ai/intake.test.ts`、`tests/domain/completeness.test.ts`

**以下为执行方自定口径，非下发要求（如实分栏，不并进 §1）**

| # | 自定内容 | 我的裁定 |
|---|---|---|
| 1 | 完整性校验**服务端拿原文重算**，不采信模型自述；图片路径 `verified=false`，前端不显示覆盖率 | **采纳**。理由是它与 §1 禁止事项④同向：让模型自评通过率等于让被考的人批自己的卷 |
| 2 | 图片长边压到 1400px、三档降级；HEIC 给可读报错；demo 模式图片返回 422 诚实失败；限流文本 12/min、图片 5/min | 采纳，但 422 那条要写进 §5 验收（"诚实失败"必须有人真的点过才算） |
| 3 | 图片入口与文本入口限流阈值不同（5 vs 12） | 采纳，理由是图片单价更高；**但这条属产品口径，未经主管书面确认** |

## 4. 我如何引导与修正

| # | 现象 | 我的判断 | 我下的指令 | 结果 |
|---|---|---|---|---|
| 1 | `选题定义书` 原 P2 明写「**不做 OCR 拍照识别课表**」，而 `api/ai/parse-image` 已落地并在用 | 不是实现越界，是**需求文档没跟上范围扩张**；两条口径同时存在，评委一读就矛盾 | 由选题官作废该条（已执行），并在需求定义书标"历史记录·双签待补" | 已修正（文档侧）；实现侧不动 |

## 6. 经验沉淀

- 同类任务要在 Prompt 里提前写死一句：**「新的输入形态必须复用既有输出契约与既有护栏，只允许在消息体和校验方式上不同」**——否则第二个入口一定会长出第二套逻辑。
