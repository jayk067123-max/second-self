## 1. 意图卡

| 项 | 内容 |
|---|---|
| **目标** | 两件事：① 能判定「某节课在某周上不上」（周次范围：起止 + 单双周 + 排除周）② 用户**重传课表**时能算清「新增 / 调走 / 删除 / 未变」，并且旧数据零迁移 |
| **上下文** | ①既有展开逻辑 `expandOccurrences`（`domain/`，002 轮的产物）②既有 `repeat` 字段结构 ③课表是"一节可以独立调动的课"，语义上**不是任务**（不带 `id/done/needsReview`）④前置轮次：001（骨架）、002（结构化） |
| **约束** | 全部纯函数；**不取系统时间**，学期开学日由调用方注入；周次过滤只准在 `expandOccurrences` 里**加一道 if**，不改现有循环结构；`repeat.weeks` 缺省 = 每周都上；不新增依赖；不改 `conflicts` / `reflow` |
| **禁止事项** | ①不许在 `domain` 里 `new Date()` / `Date.now()` ②不许把 `WeekSpec` 摊进 `Task` 顶层字段 ③不许做课程名同义合并（**高数 ≠ 高等数学**，宁可多报一条让人肉眼核对）④**不许用"删掉再新增"实现时段变更**——那会丢 `done` / `locked` 状态 ⑤不许动 002 的 `needsReview` 分支 |
| **验收标准** | ①单双周、排除周、跨学期边界各有用例 ②开学前 `termWeekOf` 返回 ≤ 0，**不冒充第 1 周** ③重传摘要文案格式固定「新增 X 节、调走 Y 节、删除 Z 节、未变 W 节」 ④换时段、换教室算**调走（updated）**，不是"删 1 + 新增 1" ⑤同名课一周两节时，先配"未变"的那一节，避免误报 ⑥旧数据无 `weeks` 字段时行为与改动前完全一致（回归用例） |
| **本轮求助点** | 只解决周次判定与覆盖计划；不要顺手改冲突检测（那是 003）、不要顺手做重排（那是 004）、不要做追问交互（那是 007） |

## 3. AI 的产出（可核事实 + 对外签名）

对外签名（即选题官的 TBD-1，也是逻辑手对齐用的那一组）：

```ts
isWeekActive(week: number, spec: WeekSpec): boolean
termWeekOf(dayKey: string, termStartDayKey: string): number
dayInWeekSpec(dayKey: string, termStartDayKey: string, spec: WeekSpec): boolean
```

- 结构：`WeekSpec` = 起止周 + 单双周 + 排除周；`weeksInSpec` / `isWeekActive` / `formatWeekSpec`
- 学期周：`termWeekOf(dayKey, 开学日)`，开学前返回 ≤ 0
- 覆盖：`planTimetableCoverage(旧课表, 新课表)` → 计划 + 摘要；`formatTimetableSummary` 直接出「新增 2 节、调走 1 节、删除 0 节、未变 5 节」
- 展开方式的建议口径：`expandOccurrences` 先用 `isoWeekdayOf` 筛星期，再用 `dayInWeekSpec` 筛周次——**只加一道 if**

**执行方自定口径（非下发，如实分栏）**

| # | 自定内容（**执行方自定，非下发**） | 我的裁定 |
|---|---|---|
| 1 | 〔执行方自定，非下发〕换时段 / 换教室 → `updated`「调走」；同名课一周两节时先配完全没变的，余下按 `星期差×1440 + 时刻差` 最近配对 | 采纳。最近配对是可解释的规则，不是拍脑袋 |
| 2 | 〔执行方自定，非下发〕课程名不做同义合并（高数 ≠ 高等数学） | 采纳，与 §1 禁止事项③一致 |
| 3 | 〔执行方自定，非下发〕`WeekSpec` = from/to + 单双周 + 排除周，缺省"每周都上"，旧数据零迁移 | 采纳，与 §1 约束一致 |
| 4 | 〔执行方自定，非下发〕覆盖**只产 plan、不执行**；执行在 data 层，让"改了什么"摘要与"撤销"用同一份数据算出来 | 采纳。这条比"顺手把执行也写了"高一个层次：摘要与撤销同源，才不会出现"摘要说调走 1 节、撤销只回滚 0 节" |
| 5 | 〔执行方自定，非下发〕重传"同一来源"判定＝`hash(入口类型 + 开学日 + 课表指纹)` | **已被 007 TBD-2b 裁定取代**：不把指纹当判定依据，界面问「这份新表覆盖哪一份」、默认上次同渠道导入那份，**指纹只算默认值** |

## 4. 我如何引导与修正

| # | 现象 | 我的判断 | 我下的指令 | 结果 |
|---|---|---|---|---|
| 1 | "周次范围展开"与 002 的 `needsReview` 分支可能重复实现（选题官列为 TBD-1） | 这是典型的**两个入口做同一件事**；不对齐签名就会长出两套 | 先冻结三个函数签名，再让展开口径"只加一道 if、不碰循环结构、`weeks` 缺省为每周" | 已约束，待逻辑手回一句确认 |
| 2 | "同一门课换了时段"该算 `updated` 还是"删 1 + 新增 1"，执行方自行定了后者之外的口径 | 若按删+新增实现，会**丢 `done`/`locked` 状态**，用户已标记完成的任务会被"重传"重置——这是数据事故，不是文案问题 | 卡里禁止"删掉再新增"；摘要必须出现「调走」这一项 | **执行方口径与我一致，但这条属它自定，需求方尚未书面确认** ——如实标注 |
| 3 | 若用"删掉再新增"实现时段变更，`done` / `locked` 会被一次重传**静默重置** | 这是数据事故，不能靠自觉防——必须**靠结构防** | 「换时段按调走算；不许用删掉再新增实现」写进禁止事项④ | **已落实在类型上**：`planTimetableCoverage` 的 `updated` 条目携带 `before.taskId`，store 走**原地 update**，不删不建——`done`/`locked` 结构上不可能被重置。这是本轮"约束真的生效"最硬的证据，比任何自述都强 |

> 第 2、3 条是本卡最值钱的两条：它们证明约束不是事后总结，而是能在实现前拦住一类数据事故；而且第 3 条已经落到了类型层——**拦得住的是结构，不是承诺。**

## 6. 经验沉淀

- 提前写死一句：**"重传是合并旧状态，不是替换列表"**——它会同时决定摘要文案、`done`/`locked` 是否保留、以及要不要给"调走"单独开一项。这一句没写，AI 十次有九次选"清空重建"。
