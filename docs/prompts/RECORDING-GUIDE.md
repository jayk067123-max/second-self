# 对话留痕规范（RECORDING-GUIDE）

> 适用：2026 全国高校 Vibe Coding 开发挑战赛 · 可复现性（25%）+ 意图控制（20%）
> 一句话：**每轮交互结束 10 分钟内归档，与 git 提交同批落地。** 过夜就算补记。

---

## 1. 归档时机

| 时机 | 动作 |
|---|---|
| 发 Prompt 前 | 建好 `NNN-<模块名>.md`，填 `TEMPLATE.md` 的 §1 意图卡 |
| AI 返回、代码跑通后 | 立刻补 §2 §3 §4 §5，截图存附件目录 |
| commit 之前 | 检查 §2～§5 无空、截图已存、INDEX.md 已更新 |
| commit 同批 | 代码 + Prompt 记录 + INDEX 一起提交，commit message 带 `[prompt:NNN]` |

**禁止**：先写完整个项目再回头补 Prompt 记录。补出来的链条时间线必然和 git 冲突。

## 2. 存放位置与命名

```
01-源码仓库/vibe-coding-2026/
└── docs/prompts/
    ├── INDEX.md                 # 总索引，每轮结束必须更新
    ├── TEMPLATE.md              # 意图卡模板
    ├── RECORDING-GUIDE.md       # 本文件
    ├── 000-project-inception.md
    ├── 001-<模块名>.md
    ├── 002-<模块名>.md
    └── 003-<模块名>.md

DS-项目集/05-Prompt与演进记录/     # 原始素材（不进 git）
    ├── 001-<模块名>/
    │   ├── P001-20261018-1432-意图卡.png
    │   ├── P001-20261018-1440-AI首版产出.png
    │   ├── P001-20261018-1505-报错.jpg
    │   └── P001-20261018-1512-修正后通过.png
    └── 录屏/
        └── P001-20261018-1430-整轮交互.mp4
```

- 源码记录用**三位序号递增**，一个编号 = 一个可验收的功能增量，**不按天不按次**。
- 序号必须和 commit message 里的 `[prompt:NNN]` 一致。
- 素材目录名与 md 文件同名，序号对齐，便于评委一对一核。

## 3. 每份记录必须包含的四要素

| # | 要素 | 具体内容 | 缺失后果 |
|---|---|---|---|
| 1 | **我的 Prompt** | 原文照贴，含多轮追问，不改错别字 | 无法证明意图由人给 |
| 2 | **AI 的建议 / 产出** | 方案摘要 + 改动文件 + 关键代码片段 | 无法证明过程真实 |
| 3 | **我如何引导修复 Bug** | 现象 → 我的判断 → 我的指令原文 → 结果 | **意图控制 20% 直接归零** |
| 4 | **最终结果** | 可运行证据 + 验收标准逐条 ✅/❌ | 无法证明改完真的对 |

## 4. 一一对应纪律（防"一次性大提交"）

每轮结束时自查三条，全过才允许提交：

- [ ] 本轮新增/修改的每个源码文件，都能在本轮 md 的 §3「改了哪些文件」里找到
- [ ] `git log --stat` 里本轮提交的改动量，与 md 描述的改动量量级一致（不允许 md 写「实现了登录」，提交里却是 40 个文件全量）
- [ ] INDEX.md 的状态列已从「进行中」改为「已归档」，并填上**提交主题**（hash 由 `docs/COMMIT-MAP.md` 统一列，本表不写死）

**发现一次性大提交的处置**：立刻拆。代码不动，但把 Prompt 记录按实际迭代顺序拆成多条，并在 INDEX 备注「事后按实际迭代拆分，非单轮产出」。**不要伪造 commit 历史**。

## 4.5 数字纪律与哈希纪律（2026-10-18 全队铁律）

材料里最容易被自己搞坏的不是内容，是**会过期的数字和会失效的哈希**。三条硬规矩：

1. **带时刻的实跑记录可以写具体数字**。如「16:10 实测 65 项」「16:35 实测 176 项」——它有时刻戳，是证据，允许精确。
2. **不带时刻的概述一律不许写死数字**。统一写「以 `npm test` 输出为准」；确需量级只写下界（如「`conflicts` 60+ 项」）。原因：同一天内该数字变过五次（54 → 65 → 122 → 149 → 176），写死必然过期。
3. **本表不写死 commit hash**。历史冻结前 hash 会变，写死会产生悬空引用；统一填提交主题，真实 hash 由 10-26 的 `docs/COMMIT-MAP.md` 一次性列全。

配套一条：**真实终端输出只做路径脱敏**（`<仓库根>`），版本号、通过数、耗时、时间戳一律保留——**脱敏路径不算造假，改写结论才是**。

**第 4 条（2026-10-18 主Bot 加为纪律，后补第四样）：报测试结果必须带坐标，坐标是四样。**

凡在消息/文档里报"测试通过"，必须同时给出：

1. **`HEAD`**（`git rev-parse --short HEAD`）
2. **时间戳**（报数那一刻）
3. **树的状态**（三选一，必写，不许用"我判断它不影响"代替）：
   - `工作区（无未提交改动）`
   - `工作区（含未提交 N 个文件：<列文件名>）`
   - `干净副本（git archive HEAD 导出）`
4. **`Test Files … / Tests …` 两行原样**

缺任一项按「未测」处理。示例：

> `HEAD 3fc31c8 · 2026-10-18 17:29:44 · 工作区（含未提交 2 个文件：docs/prompts/001-…md、docs/prompts/INDEX.md）· Test Files 12 passed (12) / Tests 221 passed (221)`

原因：同一天同一仓库被报过 176 / 216 / 221 三个值，**全都是真的**。前两样只能定位"哪个 commit"，**分不出"哪棵树"**——同一个 HEAD 下工作区有未提交改动、干净副本、另一个 worktree，项数可以不同。树的状态不写，数字就无法复现。

> 为什么这条值得写成铁律：今天所有事故的共同根因是"记得"与"实际"的偏差——有人拿旧素材状态去指挥、有人引用作废 hash、有人三次读到旧版本。**留痕体系最大的敌人不是造假，是缓存印象。**

## 5. 工具不支持导出时的取证方案

适用于网页版对话（如 ChatGPT / Claude 网页 / DeepSeek 网页）或工具无导出功能的情况。

### 5.1 截图（首选）

**每轮至少 4 张，缺一不可：**

| 顺序 | 截什么 | 画面必须能看清 |
|---|---|---|
| ① | 意图卡 / 输入框里我打的 Prompt | 我的原话全文（长 Prompt 分屏滚拍，相邻两张有重叠行） |
| ② | AI 的首版回答/首版代码 | 模型名、回答开头、关键结论 |
| ③ | 出错现场（报错 / 结果不对 / AI 写歪） | 报错信息全文、终端或界面 |
| ④ | 修正后跑通 | 运行结果 + 时间/会话标识 |

**命名**：`P<三位序号>-<YYYYMMDD>-<HHmm>-<内容简述>.png`
例：`P002-20261022-1015-AI把接口写成同步.png`

**要点**：
- 用浏览器全屏截图（含地址栏），能自证是哪个工具；
- AI 回答若提到「我改了 X 文件」，截图要能对上仓库里的实际文件名；
- 每张截图右下角若带系统时间更好，没有就在文件名里写时间。

### 5.2 录屏（整轮交互，最硬的证据）

- 触发条件：某个功能是**多轮连续调**出来的，截图讲不清演进；
- 录法：整轮从头录到尾，包含我打字、AI 输出、我改代码、我重新运行；
- 命名：`P<序号>-<YYYYMMDD>-<HHmm>-整轮交互.mp4`；
- 存 `05-Prompt与演进记录/录屏/`，mp4 超过 100MB 就压到 720p 再存。

### 5.3 网页复制留痕（次选）

- 复制 AI 回答全文到 `05-Prompt与演进记录/NNN-<模块名>/raw-回答NN.txt`；
- md 里 §3 写摘要，raw 全文作附件——摘要是给人看的，原文是给评委抽查的。

### 5.4 存哪、谁存、怎么进仓库

- 原始素材（png/jpg/mp4/raw txt）**不进 git**，存 `05-Prompt与演进记录/`；
- md 记录里写附件文件名清单，评委要查时可以现场给；
- 若要进仓库，只进压缩后的小图（≤200KB），且 md 里用相对路径引用。

## 6. 补记标注规范

- 凡事后补写的记录，在文件头「记录性质」写 **补记（补记日期 YYYY-MM-DD）**；
- §2 Prompt 原文若靠回忆重建，必须写：`【回忆重建，非原文】`；
- 补记≠造假：补记说明的是"这件事真实发生过，但原始载体没留住"。**凭空编造没发生过的对话，一律不许。**

## 7. 排期提醒：哪一批必须留真实 Bug 案例

省赛预指导（10-31）前至少 3 条完整链，建议按阶段切分：

| 编号 | 阶段 | Bug 案例来源 |
|---|---|---|
| 001 | MVP 主干跑通（选题定稿后第一版） | 环境/依赖/首屏白屏类，必出 |
| 002 | 核心功能一深化 | **刻意保留**：AI 第一版偏离验收标准的那一轮（不强求造 bug，出了就冻结记录，别重写美化） |
| 003 | 核心功能二 + 体验收敛 | 回归类：改 A 弄坏 B，记"我怎么发现并让 AI 定位" |

**纪律**：真实出错的那一轮**当场冻结**（截图 + 存 Prompt 原文），不要事后重构叙述。评委会看修复过程里你的判断力，那比"一次写对"值钱。

## 8. 待归档队列（10 分钟机制）

问题：13 天窗口下，最可能的崩法是"代码一路写，记录留到最后"——最后必然补记、必然与 git 对不上。
解法：把留痕拆成**逐事件的小动作**，用 `docs/prompts/QUEUE.md` 当实时看板。

### 8.1 触发源（任一出现即开行）

| # | 触发 | 谁发现 | 10 分钟内必做 |
|---|---|---|---|
| 1 | `git log` 出现新的非 docs 提交 | Prompt官 | 开队列行 + 查有没有对应 md，没有就建 |
| 2 | 群里说"改好了/跑通了" | 任何人 | 建素材目录，提醒改动人立刻截 4 张 |
| 3 | 用户要下发新需求 | 用户/主Bot | **先建卡再让 AI 动工**，禁止先码后卡 |

### 8.2 Prompt官每个事件的固定动作

1. `docs/prompts/NNN-*.md` 填 §1 意图卡；
2. `05-Prompt与演进记录/NNN-<模块名>/` 建同名素材目录；
3. 通知改动人截图四件套（我的 Prompt / AI 首版 / 出错现场 / 修正后）；
4. 用 `git log --stat` 对账：改动文件数是否与 md §3 描述量级一致；
5. 推进 `QUEUE.md` 状态：`⏳待建卡 → 🟡已建卡·待素材 → 🟠素材齐·待对账 → ✅已归档`。

### 8.3 三条红灯（发现即当场提，不等收尾）

- md 说实现了某个功能，提交里查不到对应用文件；
- 单个提交里混了 3 个以上不同模块的改动（一次性大提交）；
- 素材目录空着，md 却写"已归档"。

### 8.4 为什么不用"每天结算"

每天结算会积压，且当天记不清细节。改成"事件触发 + 10 分钟"，每次只花 5 分钟，且截图还在屏幕上、Prompt 还能原文复制——这是本机制唯一的价值点。
